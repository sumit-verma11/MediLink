# MedLink Roadmap (Phases 2–7 overview)

> This is a sequencing/tracking document, not an execution plan. Each phase gets
> its own detailed, bite-sized task plan (in this same folder) written **right
> before that phase starts** — not now — because each phase's exact files,
> interfaces, and test data depend on decisions made while building the phase
> before it. Phase 1's detailed plan is `2026-07-27-phase1-foundation.md`.

## Scope decision carried over from Phase 1

CLAUDE.md §6 specifies a full relational seed dataset (appointments, triage
sessions, prescriptions, lab referrals/bookings, ratings, notifications)
that spans every phase's data. Building that all in Phase 1 would mean
guessing at shapes for workflows (booking, triage, prescriptions, referrals)
that don't exist as code yet. Instead, **each phase's plan adds its own
slice of the §6 seed data** once that phase's models/routes are locked in:

| Phase | Seed data it adds (from CLAUDE.md §6.4) |
|---|---|
| 1 | Accounts, doctor/lab profiles + test catalogs, notifications |
| 2 | 15 appointments (6 completed, 3 confirmed, 2 requested, 1 rejected, 1 cancelled, 1 no-show, 1 completed-without-prescription) |
| 3 | 4 triage sessions (3 linked to specialties, 1 red-flag emergency case) |
| 4 | 6 prescriptions with realistic generics |
| 5 | 3 lab referrals (report_ready / booked / sent) + lab bookings incl. 1 walk-in |
| 6 | 8 ratings, AuditLogs review pass, final notification sweep |

## Phase 2 — Availability & Booking Engine
**Depends on:** Phase 1 auth, RBAC, DoctorProfile.
**Builds:** `AvailabilityRule` CRUD for doctors, a slot-generation service (rules →
concrete 14-day slot list minus booked/blocked), Redis-based slot locking
(`SET slot:{doctorId}:{slotStart} patientId NX EX 300`), the booking state
machine (requested → confirmed/rejected → completed/cancelled/no_show) with
embedded `timeline`, Socket.io live dashboard updates, and Nodemailer
notifications + a node-cron 24h reminder job.
**Hardest engineering risk:** the double-booking race — the plan must include
a concurrency test that fires two parallel booking requests at the same slot
and asserts exactly one succeeds.
**Definition of done:** two browsers racing for the same slot — one wins, one
gets a clean error; doctor confirm/reject flips patient's dashboard live.

## Phase 3 — AI Triage & Doctor Matching
**Depends on:** Phase 1 DoctorProfile (specialties, city, fee), Phase 2 slots
(triage "book with Dr. X" deep-links into booking).
**Builds:** FastAPI service scaffold (internal-only Docker network), the
curated `specialty_map.json` (~40 specialties), a red-flag keyword layer that
runs *before* embeddings, the sentence-transformers (`all-MiniLM-L6-v2`)
cosine-similarity matcher, the `/triage` endpoint, a Next.js chat UI, and a
Node→FastAPI proxy with timeout + circuit breaker that falls back to a manual
specialty picker if the AI service is down.
**Key artifact:** `apps/ai/tests/fixtures/triage_cases.json` — 50 labeled
cases (≥3 per specialty + 5 red-flag cases), target ≥90% top-3 accuracy.
**Definition of done:** "itchy red patches, 2 weeks" → Dermatology (0.87) → 3
bookable dermatologists; "crushing chest pain" → emergency banner, no matching.

## Phase 4 — Prescriptions
**Depends on:** Phase 2 `Appointment` (status must be 'confirmed'), Phase 1
DoctorProfile (letterhead fields, reg no).
**Builds:** prescription composer (doctor-only), a seeded generic-drug
autocomplete list, PDF generation via pdf-lib (letterhead, signature image,
QR → `/rx/verify/{id}`), the immutable/"amend creates v2" rule, patient
prescription list + health timeline, and the auto-transition of the
appointment to 'completed' on prescription creation.

## Phase 5 — Lab Referral Flow
**Depends on:** Phase 4 `Prescription.recommendedTests`, Phase 1 `LabProfile`
test catalogs.
**Builds:** lab-matching-by-test-code, `LabReferral` creation with a nanoid
token, the public `/r/{token}` landing page (tests pre-selected, prices
totaled), the lab dashboard status pipeline (booked → sample_collected →
report_ready with PDF upload), dual notifications on report upload (patient +
referring doctor), the referral status timeline on the doctor's side, and the
walk-in-booking-without-referral path.

## Phase 6 — Polish, Admin, Deploy
**Depends on:** everything above being demoable end-to-end.
**Builds:** the `Rating` model (not present in CLAUDE.md §1 — first defined
here) + post-completion rating flow + `avgRating`/`ratingCount` recompute,
admin analytics (registrations, appointments/day, top specialties,
triage→booking conversion), the notification bell/mark-read center, global
search (doctors by name/specialty/city, labs by test), a security pass (rate
limits per route, NoSQL-injection review, upload validation, CORS lockdown),
final deploy wiring (Vercel + Render/Railway + Atlas + Upstash), and the CI
workflow's build/push-image step.

## Phase 7 — Optional differentiators (post-launch)
Not sequenced — pick opportunistically after Phase 6 ships: FHIR-lite export
endpoint, "AI suggests, doctor approves" prescription pre-fill (flagged),
Telegram bot notifications, Hindi triage via multilingual MiniLM, doctor
earnings/analytics.
